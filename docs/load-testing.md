# 自动压测

在管理页打开“压测”，勾选当前环境已发布、启用且未归档的 Agent，填写每个 Agent 的模拟用户数、单沙箱 CPU 核数和内存 MiB，然后点击“开始压测”。同一个 Agent 的测试用户使用该行资源设置，不改变 Agent 默认配置，也不复用正常用户的沙箱。

每个模拟用户名对应一个独立沙箱和一个新会话，不创建新的登录账号。模型使用所选 Agent 当前生效的默认模型；MCP、Skills、Hook 也沿用当前生效版本。固定请求不要求工具调用：

```text
This is a load test. Do not use tools, ask questions, or request permission. Reply with exactly: LOAD-TEST-OK
```

压测会产生真实模型调用。页面显示计划沙箱数、CPU/内存配额合计，以及服务器实时资源状态。超出可分配预算时禁止启动，并显示其他行不变时每个 Agent 最多能选择的用户数。

## 服务器健康与容量检查

“服务器资源状态”每 5 秒更新，也可手动刷新。显示 CPU 使用率、实际可用内存、已分配配额、系统预留、剩余可分配 CPU/内存和运行中的沙箱数。CPU 瞬时空闲不等于可分配核数，页面分别展示。

预算统计 Docker 宿主机上的运行容器，也计入已停止但仍可重启的沙箱配额。内存同时检查总配额余量和实际 `MemAvailable`，扣除已有容器尚未使用、未来可能增长的内存配额；文件缓存不重复计算为可用余量。系统预留取固定下限与总容量比例的较大值。可在服务器 `config.cfg` 调整，重启控制器后生效：

```ini
[load_capacity]
reserved_cpu = 1.0
reserved_memory_mb = 1024
reserve_fraction = 0.1
max_cpu_usage_percent = 90.0
```

默认至少预留 1 核、1024 MiB，且各不少于总容量的 10%。CPU 使用率达到 90%、已有配额侵占预留、沙箱缺少资源上限、采样失败或数据超过 15 秒时，禁止启动。旧配置没有此节时采用上述默认值。监测的是 Docker 所在的 Linux 宿主机；Docker 与本地 `/proc` 容量不一致时拒绝估算。

服务器在创建测试用户前重新采样和校验，不能通过直接调用 API 绕过。准备过程每批最多创建 4 个沙箱，每批前检查所有尚未创建用户的总需求；准备完成后、发起模型请求前再次检查。中途资源不足会停止后续创建和本次生成，保留已创建数据供管理员清理；报告记录容量快照和阻止原因。

这些检查是保守的准入预算，不是操作系统资源预留。普通聊天、宿主机进程及未设置上限的基础服务仍可能继续占用资源，因此不能保证运行中绝不 OOM；建议从少量用户逐步增加。

## 执行与报告

服务器先以最多 4 路并发准备沙箱和会话，准备阶段结束后同时释放所有已就绪用户的请求。每用户只提交一次，不重试模型请求；准备失败的用户仍计入总数。同步释放不保证发起时间差为零，报告会显示实际差值。

默认每 Agent 1 用户、1 CPU、1024 MiB。单任务最多 100 用户，CPU 范围 0.25～64 核、内存 256～65536 MiB。请求默认 180 秒超时，可改为 10～1800 秒；会话准备默认 120 秒，API 可设置为 10～300 秒。

报告包含：

- 总体和按 Agent 汇总的准备数、请求数、成功数、失败数、取消数与成功率。
- 成功请求的平均耗时、P50/P95/P99，采用最近秩分位数；不包含沙箱准备耗时。
- 从首次请求发起至最后请求结束的成功吞吐量，以及各请求发起时间差。
- 每个用户的沙箱 ID、会话 ID、资源配额、准备耗时、请求耗时、Token 数与错误分类。
- 启动时的 `admission_capacity` 与准备过程中的 `capacity_checks`；容量变化阻止执行时记录 `capacity_blocked`。
- JSON 完整报告和 CSV 用户明细下载。HTTP 200 内携带原生模型错误仍计为失败；成功表示得到非空回复，不要求模型逐字遵循标记，`response_matches` 单独记录标记匹配。

这是服务端发起的控制器、沙箱与模型链路测试，使用同一套公开会话路由、认证、模型分配和工作区绑定逻辑。它不测浏览器渲染、公网网络或 Nginx 入口，不报告首 Token 延迟。准备耗时是当前镜像和宿主缓存条件下的实测，不代表从零下载镜像的耗时。

## 停止、重启与清理

一次只运行一个压测任务。测试期间普通聊天仍可使用；配置发布共用锁，排队等待测试结束，避免中途改变实验条件。对参与压测的 Agent 做归档或沙箱启停操作时，服务器要求先停止压测；其他 Agent 的运维操作仍可排队。压测沙箱不自动恢复，避免隐藏异常。管理员可以停止压测；准备中的 Docker 创建须先结束，才允许清理，防止清理后又出现容器。

请求超时或取消时会尝试调用原生会话终止接口。如果无法确认终止，用户明细会提示清理沙箱。控制器重启后，未完成压测标记为“已中断”，不重放请求。历史报告仍可查看；进程中断前已提交的模型请求可能需要手动销毁测试沙箱来终止。

测试结束保留数据。打开报告，在“销毁本次测试数据”输入完整测试 ID，再确认销毁。只删除该次测试的容器、会话、工作区和运行状态目录；Agent、全局资源、普通用户数据和报告均保留。`loadtest-` 是模拟用户专用前缀，测试用户不接受手工附件上传。清理后旧用户名无法再创建会话或通过文件接口重新创建目录。

清理失败会保留状态，可以使用相同测试 ID 重试。已有请求仍持有测试沙箱时先拒绝清理；容器归属不匹配或用户目录被替换为符号链接也会拒绝删除。报告元数据中的用户名、资源配额及测试结果保留，用于追溯，不代表用户工作区仍存在。

## API 与验证

接口详见根目录 `02_api_contract.md` 的自动压测章节；本地 Web 沿用 `/remote` 同源转发。该功能是后续源码改动，之前生成的 0.3.0 ZIP 不包含它；请按 `docs/build-from-source.md` 在新的输出目录重新构建后部署服务端和 Web。

```bash
python -m pytest tests/unit/test_load_tests.py tests/unit/test_load_capacity.py -q
python scripts/verify-load-testing.py
```

第二条要求 Linux、Docker、已构建运行镜像，以及当前 `config.cfg` 所指向的可用模型网关。它创建隔离的测试控制器实例，对已有示例 Agent 运行两个用户，核对真实 Docker 限制、报告和清理，不操作生产实例；结果保存在 `artifacts/web/load-testing-verification.json`。
