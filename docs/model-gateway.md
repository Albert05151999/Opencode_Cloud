# 模型网关部署与自动验证

LiteLLM 固定为 `1.98.0`，镜像摘要记录在 `versions.env` 与 Compose 中。升级时必须更新二者并重新运行验证，离线打包应保存该摘要对应镜像；验证过程不需要供应商密钥。

在 Ubuntu WSL 的 controller 虚拟环境内安装项目及测试依赖后，运行：

```sh
python scripts/verify-litellm.py
```

脚本启动两个可控后端与固定镜像的 LiteLLM，验证四个逻辑模型、流式首 token、8 路并发、故障重试/冷却、Prometheus TTFT，并保存 `artifacts/litellm/report.json` 和 `metrics.prom`。结束时清理测试容器；失败时保留失败报告与容器日志。请勿与正式网关同时占用 4001。

正式连接模型时，复制 `deploy/.env.example` 为被 Git 忽略的 `deploy/.env`，填写模型名称、两个等价部署的 API 地址和密钥。当前模板使用共享供应商密钥，若后端凭据不同，应分别引用独立环境变量；密钥不进入控制器配置、Agent 定义或镜像。然后运行：

```sh
bash scripts/model-gateway.sh config --quiet
bash scripts/model-gateway.sh up -d --wait --wait-timeout 60
```

脚本自动检测 Docker 默认 bridge 地址。LiteLLM 内部监听 4000，宿主发布至 `127.0.0.1:4001` 和 bridge 地址的 4001；Agent 使用 `host.docker.internal:4001`。默认模板用于本机可信网络，尚未加入网关身份认证。四个逻辑组各有两份等价部署，无跨逻辑组回退。健康探针使用不调用模型的 `/health/liveliness`；指标抓取需跟随 `/metrics` 到 `/metrics/` 的重定向。

网络构建问题：本机代理对 GHCR blob 曾返回 EOF。`configure-docker-proxy.sh` 将 `ghcr.io` 与 `.githubusercontent.com` 加入 `NO_PROXY` 后，固定镜像拉取通过。该设置是本机已验证方案，部署到不同网络时按实际连通性调整。

第 27 阶段的外部模型基线入口为 `python scripts/verify-model-baseline.py --source-label <提供商或部署说明>`，默认每个逻辑模型采集 20 次流式请求，保存 p50/p95、逐请求 JSON/CSV 和前后 Prometheus 快照。`source-label` 只填写非敏感部署说明。必须先配置实际后端并启动网关；没有真实后端时，只能运行 `verify-load-client.py` 的本地冒烟，不能把其结果写成外部模型基线或最终性能验收。
